# 공격·이동 결과 지연 개선 상세계획

작성: 2026-11-02. 상태: **사용자 구현·배포 지시로 구현·검증 완료, 배포 진행**. [작업 기록](UPDATE_2026-11-02_ACTION_LATENCY.md)이 아래 계획 작성 당시의 상태에 우선한다.

## 1. 목표와 근거

공격·이동 버튼을 누른 뒤 서버가 확정한 결과를 가능한 한 빨리 보여준다. 결과 표시와 최신 전황 확인을 분리하되, 오래된 병력 상태로 다음 명령을 실행하거나 같은 공격을 두 번 실행하지 않게 한다. 전투 규칙·확률·쿨타임·병력·기록은 변경하지 않는다. 구현 후에는 진행 중인 시즌에 적용할 수 있는 성능·편의 개선이다.

[읽기 전용 조사](PERFORMANCE_REVIEW_2026-11-02_ACTION_LATENCY.md)에서 서버 응답 중앙값은 직전 3.71초, 직후 4.80초였다. 직후 표본은 11건이며 여러 명령과 규칙 거절을 포함하므로 지도 변경이 원인이라고 단정하지 않는다. 실제 모바일 클릭부터 결과 표시까지는 아직 측정하지 못했다.

확인된 구조:
- 서버가 명령 저장과 기록 피드 등을 처리한 뒤 응답한다.
- 클라이언트는 성공 응답 후에도 전황과 채팅을 다시 읽는 `retryRead()`를 기다린다.
- 서버는 CPU 0.1666, 최대 인스턴스 1, 동시 요청 1로 운영 중이다. 대기열·초기 기동이 원인인지는 추가 측정이 필요하다.
- 세력명 표시는 새 DB 조회를 추가하지 않는다. 지도 기능을 제거하거나 축소하는 것을 기본 해결책으로 삼지 않는다.

## 2. 이용자가 보게 될 동작

| 단계 | 화면 | 명령 가능 여부 |
| --- | --- | --- |
| 버튼 클릭 | 즉시 ‘공격 처리 중…’ 또는 ‘이동 처리 중…’ | 같은 명령 중복 클릭 차단 |
| 서버 성공 응답 | 공격은 확정 전투 결과, 이동은 도착지·인원 안내 | 전황 확인이 남으면 새 변경 명령 대기 |
| 전황 확인 중 | 작은 ‘결과 저장 완료 · 전황 반영 중…’ 표시 | 지도 탐색·결과 닫기·채팅 열람 가능 |
| 최신 전황 확인 완료 | 병력·쿨타임·소유권 갱신, 안내 해제 | 기존 규칙상 가능한 명령 재개 |
| 동기화 지연·실패 | ‘명령은 완료됐습니다. 최신 전황을 확인 중입니다.’와 확인 버튼 | 공격 재전송 없이 조회로 복구 |
| 응답 유실로 처리 여부 불명 | ‘명령 결과 확인 중…’ | 같은 요청 번호로만 복구 |

전투 주사위 연출 750ms는 서버 지연과 별도로 측정한다. 연출 시간을 늘리지 않으며, 동기화 때문에 연출이나 결과를 다시 처음부터 보여주지 않는다. 일반 이동 성공 문구와 도착지 선택은 한 번만 반영한다.

## 3. 구현 범위와 설계

### A. 서버 확정 결과를 먼저 전달

1. `FirebaseStore.performCampaign()`의 성공 결과 반환을 후속 전황 조회와 분리한다. 성공을 확인한 즉시 해당 미확인 요청을 정리하고 확정 결과를 UI에 전달한다.
2. 서버 응답에는 기존 `result`, `event`를 유지하고, 검증 가능한 작은 확정 정보(시즌 ID, 요청 ID, 확정 revision, 해당 군주 commandSeq)를 추가한다. 전체 전장이나 채팅은 응답에 싣지 않는다.
3. `app.js`의 `run()/submit()`에서 ‘서버 처리 중’과 ‘확정 후 전황 확인 중’을 별도로 관리한다. `busy` 해제만으로 다음 명령이 가능해지지 않게 공통 저장 가능 검사에도 동기화 잠금을 적용한다.
4. 공격 결과는 응답에 포함된 해당 요청의 전투 기록을 사용한다. 실시간 전황의 마지막 명령이나 다른 전투를 대신 표시하지 않는다. 즉시 표시할 세부 결과가 없는 중복 요청 복구라면 해당 기록만 조회하고 결과를 추측하지 않는다.
5. 여러 탭·중복 응답·실시간 반영으로 같은 결과 창을 반복해서 열지 않도록 시즌/요청 ID 기준으로 중복 표시를 막는다.

### B. 받은 전황 재사용, 불필요한 재조회 제거

1. 기존 `WorldReader`의 일관성 검사를 통과한 전황만 사용한다. 분리된 구독 데이터 일부가 도착한 것만으로 완료 처리하지 않는다.
2. 같은 시즌이고 응답의 확정 revision 이상이며, 해당 군주의 순번/영수증도 모순이 없으면 이미 도착한 전황으로 확인을 끝낸다. 전역 revision 증가만으로 내 명령 성공을 추정하지 않는다.
3. 성공 응답 전에 전황 구독이 먼저 도착한 경우도 재사용한다. 동기화 시작 전 상태 검사와 구독 등록 뒤 재검사를 수행해 신호를 놓치지 않는다.
4. 아직 반영되지 않았다면 실시간 수신을 짧게 기다린 뒤 전황만 보충 조회한다. 초기 기준은 최대 500ms이며 관평 선택 대기가 포함되면 즉시 보충 조회한다. 이 대기는 결과 표시를 막지 않는다.
5. 후속 조회는 같은 시즌·목표 revision에 대해 하나만 실행한다. 기존 연결 복구 조회도 합치되, 명령 확정 이전에 시작된 읽기가 오래된 결과를 반환하면 확인 완료로 사용하지 않는다.
6. 일반 공격·이동 완료를 이유로 채팅을 다시 읽지 않는다. 채팅은 기존 실시간 구독을 이용하고 최초 접속·연결 복구·명시적 채팅 오류 복구 때만 필요한 읽기를 수행한다. 채팅 준비 여부와 전황 확인 여부를 분리한다.
7. 늦게 끝난 읽기가 더 최신 전황을 덮어쓰지 않게 revision과 시즌을 검사한다. 로그아웃·시즌 변경·스토어 종료 시 대기 작업과 리스너를 정리한다.

### C. 확정 후 지연과 미확인 명령 구분

- 성공 응답을 받은 요청은 후속 조회 실패 때문에 다시 미확인 공격으로 바꾸지 않는다.
- 새로고침해도 ‘확정됐지만 화면 반영 대기’와 ‘처리 여부 불명’을 구분할 수 있도록 최소 메타데이터를 계정·시즌별로 보관한다. 전투 전체나 전체 DB를 중복 저장하지 않는다.
- 확정 후 복구는 조회만 수행한다. 실제 응답 유실 복구는 기존 요청 ID와 seq를 유지하며, 새 ID로 공격을 재실행하지 않는다.
- 오래된 영수증이 제거됐더라도 군주 순번이 앞섰으면 재실행 불가로 정리한다. 순번만으로 과거 공격이 성공했다고 표시하지 않는다.
- 자동 보충 조회는 한 작업에서 최초 1회와 추가 2회(2초·5초 간격)를 상한으로 한다. 실시간 반영이 먼저 오면 취소한다. 실패가 계속되면 수동 확인/재연결을 안내하고 무한 조회하지 않는다.
- 결과 확정 정보가 없는 이전 서버 응답도 정상 처리한다. 이 경우 안전한 기존 확인 경로를 유지하되 확정 결과 표시를 불필요하게 늦추지 않는다.

### D. 관평·포로·시즌 종료 등 후속 화면 보존

- 관평 10초 선택은 기존 서버 마감 시각을 기준으로 남은 시간을 표시한다. 결과 표시가 빨라졌다는 이유로 새 10초를 시작하지 않는다.
- 호위 선택이 생긴 경우 관련 전황 확인을 우선한다. 확인 즉시 선택 UI를 노출하고, 선택 후에는 기존 서버 검증을 거친다. 다른 명령과 겹치거나 오래된 결과 창이 선택 UI를 가리지 않게 한다.
- 시간이 이미 만료됐으면 기존 자동 선택 결과를 표시한다. 클라이언트 지연을 이유로 서버 규칙을 바꾸지 않는다.
- 포로 처우·점령 후 도시 선택 등 추가 명령은 최신 상태 확인 후 활성화한다. 결과창 자체는 그 전에 열 수 있다.
- 시즌 종료 응답에서는 승리 안내와 최종 전황을 연결하고 새 공격을 막는다. 이전 시즌의 느린 응답이 새 시즌 화면을 덮지 않게 한다.

### E. 서버 내부 중복 처리 절감

먼저 동일 조건의 로컬 측정으로 반복 정규화·명단 조회·전장 순회 중 비용이 큰 부분을 찾는다. 같은 계산 단계에서 재사용 가능한 값만 묶어 계산한다. 트랜잭션 재시도 시에는 새 입력 상태에서 다시 계산하며 이전 상태의 결과를 재사용하지 않는다.

`server/campaign-command.js`, `server/reward-transaction.js`와 규칙 엔진의 실제 원본을 수정 대상으로 삼고, 생성된 함수 번들은 기존 빌드 도구로 갱신한다. 저장 원자성, 난수 입력, 충원·퇴각·포로 처리 순서와 반복 요청 결과는 보존한다.

기록 피드·공지 저장을 함수 응답 뒤에 방치하는 방식은 사용하지 않는다. 전달 보장 없이 응답을 먼저 끝내면 기록이 유실될 수 있다. 전체 DB 구조 변경, 신규 큐 서비스 도입, 장기 전장 캐시로 판정하는 방식은 이번 1차 개선 범위에서 제외한다.

## 4. 계측과 완료 기준

첫 기준 측정은 로컬/에뮬레이터에서 동일 전황·명령·난수로 수행한다. 운영에서는 이용자의 정상 플레이를 수동 공격 없이 표본 확인한다.

| 지표 | 구분/기준 |
| --- | --- |
| 클릭 → 서버 호출 시작 | 중복 로컬 작업·직렬 대기 구분 |
| 서버 호출 → 응답 | 초기 기동/따뜻한 실행, 공격/이동, 성공/거절 별도 집계 |
| 함수 진입 이후 | 전장 준비, 규칙 계산, 저장, 기록 피드 등 단계별 측정 |
| 성공 응답 → 결과 표시 | 개발 기준 환경에서 200ms 이내를 목표. 후속 조회를 고의로 늦춰도 결과 표시가 기다리지 않을 것 |
| 성공 응답 → 다음 명령 가능 | 실제 최신 전황 확인 후에만 잠금 해제 |
| 명령당 추가 읽기 | 실시간 반영 완료 사례 0회, 일반 공격·이동 후 채팅 강제 읽기 0회 |
| 정확성 | 중복 전투·병력 복제/손실·오래된 전황 덮어쓰기 0건 |

개발 환경은 상세 시간 측정을 사용한다. 운영 서버 시간 로그가 필요하면 정상 요청 최대 5% 표본, 실행당 작은 구조 로그 1개로 제한하고 전황 본문·군주 이름·채팅·인증값은 남기지 않는다. 클라이언트 측정은 로컬 개발 진단을 우선하며 새 원격 분석 서비스를 도입하지 않는다. 단계 시간이 없는 구간을 서버 대기열 시간이라고 단정하지 않는다.

배포 전후 통계는 명령 종류·성공 여부·초기 기동을 구분하고 표본 수·기간을 함께 적는다. 가능한 정상 공격/이동 각 30건이 쌓이면 중앙값·95백분위를 비교하되, 이용이 적으면 적은 표본이라는 한계를 보고한다. 이 표본 수는 배포 선행 조건이 아니다. 전체 응답을 몇 초로 보장하지 않으며 결과 표시 지연 제거와 서버 시간 감소를 구분해 보고한다.

## 5. 검증 목록

1. 성공 응답 전/후 실시간 전황 도착 순서를 바꿔도 같은 결과 1회만 표시.
2. 전황 조회 5초 지연·실패, 채팅 조회 실패에도 확정 결과 즉시 표시. 전황 확인 전에는 새 저장 명령 차단.
3. 빠른 연속 클릭·다중 탭·재접속·응답 유실·확정 후 새로고침에도 공격/이동 한 번만 적용.
4. 오래된 읽기·다른 계정/시즌 데이터·seq만 앞선 요청·100개 뒤 영수증 제거 시 안전 복구.
5. 구독 지연·350ms 기록 피드 보충·분리 데이터 도착에도 기존 일관성 검사 유지.
6. 장수만 이동, D4 동반 이동, 포화 도시 교환, 개인/도시 쿨타임, 승리/패배·퇴각/관평/포로·시즌 종료 회귀 검증.
7. 동일 전황/난수에서 최적화 전후 병력·피해·점령·보상·기록·순번 결과 일치. 트랜잭션 충돌 재시도 포함.
8. 모바일/PC에서 결과창·처리 중 안내·지도 선택·채팅·관평 선택 확인. 실제 브라우저를 사용할 수 없으면 대체 검증 범위와 미확인 사항을 보고.

단위 테스트, 필요한 함수/스토어 통합 테스트, Firebase 에뮬레이터 규칙 검사, 빌드를 수행한다. 운영 전장에서 테스트 공격·이동·보상 사용은 하지 않는다.

## 6. 작업 순서와 배포

1. 기존 동작의 시간 측정과 지연/응답 역전 재현 테스트 작성.
2. 확정 응답 메타데이터 및 클라이언트 동기화 상태 모델 구현.
3. 결과 먼저 표시, 다음 명령 잠금, 실시간 전황 재사용, 채팅 재조회 분리.
4. 관평 등 후속 화면과 실패 복구 검증, 측정된 서버 중복 계산만 최적화.
5. 회귀/규칙/UI 검증과 배포 산출물 확인.
6. 사용자 구현·배포 지시 이후 서버를 먼저 호환 가능하게 배포하고 사이트를 배포. 이전 클라이언트와 추가 메타데이터 호환 확인.
7. 공개 파일 버전·핵심 화면을 확인하고 전체 채팅·전황·접속 알림에 변경 내용 안내. 실제 측정된 개선과 남은 한계 보고.

문제가 생기면 이전 검증 코드로 되돌리되 현재 영토·병력·전적을 백업으로 덮어쓰지 않는다. 새 클라이언트는 추가 메타데이터가 없는 서버 응답도 처리하도록 한다.

## 7. 자원·비용 방침

1차는 추가 조회와 중복 계산을 줄이는 코드 개선으로 진행하며 현재 CPU·최소/최대 인스턴스·동시 요청 설정은 유지한다. 추가 계측 로그에도 소량의 비용 가능성이 있으므로 표본·크기를 제한한다.

개선 후에도 서버 계산/대기열이 주된 원인으로 확인되면 서버 자원 조정을 별도 후속 항목으로 제시한다. 최소 인스턴스 상시 운영이나 동시 실행 확대를 이번 계획만으로 적용하지 않는다. 비용 가능성은 안내하되 사용자가 지시한 구현을 자동 중단하는 조건으로 삼지 않는다.

이번 작업은 상세계획 문서 작성이며 게임 코드·서버 설정·운영 데이터는 변경하지 않았다.
