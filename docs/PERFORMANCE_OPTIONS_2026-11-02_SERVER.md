2026-11-02 20:23 KST, 배포한 campaignOrder의 약5% 표본 로그를 한 번 조회했다. 조회된 기록은2건이다.

두 건 모두 정상 처리됐다. move는 공격과 아군 이동이 같은 명령 종류이므로 이 로그만으로 둘을 구별하지 않는다. 표본2건은 평균 체감시간이나 모든 명령의 병목을 확정할 근거가 아니다. 콜백 계산 외 시간이 크다는 관찰이며 나머지 전부를 DB 네트워크 시간이라고 단정하지 않는다. 데이터 준비·직렬화·SDK 처리·서버 검증·통신 등이 포함된다. 이 측정은 클라이언트 왕복/결과 연출이나 함수 진입 전 대기시간을 포함하지 않는다.

## 기존 저장 사본 크기

2026-11-02 20:14:52 KST 공지 직전 보존한 로컬 사본을 분석했다. 운영DB를 새로 내려받지 않았다. JSON UTF-8 직렬화 크기이며 실제 과금 바이트/전송 압축량과는 다르다.

- 전체493,233바이트.
- history293,748바이트(100개 기록, 약59.6%).
- territories161,330바이트(약32.7%).
- 나머지는 영수증·참가자·무장 색인 등이다.

클라이언트는 이미 요약 피드와 기록 개별 조회를 사용하지만, 명령 서버는 여전히 history를 포함한 전장 루트에 트랜잭션을 수행한다. 클라이언트 기록 캐시만 늘리는 것과 서버 명령이 다루는 데이터 경량화는 효과가 다른 작업이다.

## 추천 우선순위

1. **서버 명령 대상 데이터 경량화.** 큰 전투 상세를 활성 전장 트랜잭션 밖으로 분리하고 현재 판정에 필요한 상태와 작은 기록/참조만 남기는 구조를 검토한다. 화면에서는 기존100개 기록과 주사위 상세를 계속 조회할 수 있게 한다. 상세 기록의 전달을 보장하는 저장 설계와 중복·충돌·구버전·이관 검증이 선행돼야 한다. 전투/퇴각/포로/보상에 필요한 현재 상태를 분리 저장해 원자성을 깨는 방식은 피한다. 사본의59.6%가 분리 가능한 양의 참고치이며, 전송량이나 시간을 같은 비율로 줄인다는 보장은 아니다.
2. **서버 중복 계산 줄이기.** normalizeWorld가 명령 전후에 실행되고 충원 처리에서도 색인·담당 계산이 반복되는 경로를 로컬 프로파일링한다. 같은 입력에서 동일한 결과를 재사용할 수 있는 부분만 최적화하고, 다른 명령/트랜잭션 재시도의 변경된 상태에는 캐시 결과를 재사용하지 않는다. 이 표본의 계산 시간0.6~0.8초만으로 전체5~6초를 설명할 수는 없다.
3. **명령 함수만 CPU 상향 비교.** campaignOrder의 현재 약1/6CPU와1CPU를 비교하는 후보. 최소 인스턴스0을 유지하면 유휴 상시 대기는 추가하지 않지만 실행 단가는 높아진다. 실행시간 단축을 포함한 실제 총비용은 별도로 비교해야 한다. 전장 전송/저장 구간이 지배적이면 CPU만 늘려도 개선이 제한될 수 있다. AI/다른 함수까지 일괄 상향할 이유는 없다.
4. **첫 명령이 특히 느릴 때 상시대기1개 검토.** 초기 기동 지연을 줄이는 수단이며 유휴 비용이 발생한다. 모든 명령의 DB 처리시간을 해결하지는 않는다. 친구끼리 비정기 접속하는 게임에서는 앞선 개선을 우선한다.
5. **동시 요청 대기는 경량화 후 검토.** 현재 최대 인스턴스1·동시 요청1이다. 늘리면 다른 요청이 앞에서 끝나기를 기다리는 시간이 줄 수 있지만 동일 전장 루트 트랜잭션의 충돌·재시도도 증가할 수 있다. 관찰한 두 표본에는 콜백 재시도 증거가 없다. 함수 내 동시성 상향은 전역 난수 설정 등 공유 상태의 요청 격리 검토도 필요하다. 무조건 동시성 수치를 높이는 것을 첫 해법으로 채택하지 않는다.

추천 순서는 **활성 전장 경량화 → 중복 계산 절감 → 필요 시 명령 함수만 자원 비교**다. 첫 실행만 느린 양상이 확인될 때 상시 대기를 따로 검토한다. 정량 목표는 상세계획 단계에서 동일 전황 비교로 정하며1초 이하 같은 결과를 보장하지 않는다.

## 공식 자료 확인

- [Firebase 함수 자원·최소 인스턴스·동시 요청 관리](https://firebase.google.com/docs/functions/manage-functions): 최소 인스턴스는 유휴 비용 발생, fractional CPU는 함수 내 동시 요청 비활성, CPU 설정별 차이와 테스트 권고.
- [Realtime Database 트랜잭션](https://firebase.google.com/docs/database/web/read-and-write#save_data_as_transactions): 충돌 시 현재 데이터로 콜백 재실행, 원자적 처리 보존 필요.
- [함수와 데이터 위치](https://firebase.google.com/docs/functions/locations): 서비스 간 위치가 다르면 지연/비용 증가 가능. 현재 설정은 함수와DB 모두asia-southeast1이므로 단순히 함수를 한국으로 옮기는 것을 기본 개선안으로 제안하지 않는다.

이번 요청으로 구현·배포나 서버 자원 조정은 하지 않는다. 테스트 명령도 운영 전장에 실행하지 않았다.
