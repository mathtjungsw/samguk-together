# 서버 속도 개선 · 2026-11-02

사용자가 추가 추천안의 개발·배포를 직접 지시했다. 구현·검증·서버/사이트 배포·현재 시즌5 기록 분리 활성화·전체 공지 완료.

## 구현

- 현재 전장의 전투 기록은 작은 요약과detailVersion을 유지하고, 주사위·병력 사본 등 상세는battleRecords/시즌/기록/불변버전에 저장한다.
- 새 상세는 게임 명령의 같은 트랜잭션에서recordOutbox에 확정된다. 외부 상세 저장과 대기 항목 제거는 하나의 원자적 업데이트다. 전달 실패 시에도 대기에 원본이 남고 조회할 수 있으며 다음 명령/AI 작업에서 재시도한다.
- 기록 수정은 새 불변 버전으로 저장해 늦은 게시가 최신 기록을 덮지 않는다. 최근100개에서 빠진 상세 버전은 삭제 대기에 넣어 정리한다.
- 등록·충원·강화·보상·포로·공격·AI 등의 게임 상태는 기존 트랜잭션과 규칙을 유지한다. 과거 전투 주사위 사본만 분리한다. 관평 선택을 위한 진행 중 전투는 현재 전장에 유지한다.
- 명령 응답에는 기존 확정 전투 상세를 유지한다. 기록 다시보기는 새 경로→전달 대기 원본→새 경로 재확인 순서로 읽고 기존 형식 폴백·로컬 캐시를 유지한다.
- 군주마다 전체 영토와 병력을 반복 조회하던 집계를 한 번의 순회로 줄였다. 영토 수·군주 위치 결과가 기존 계산과 같음을 대조했다. 입출력 정규화·중복 무장 검증은 유지한다.
- campaignOrder만 CPU약1/6→1로 변경했다. 메모리256Mi·동시1·최소0·최대1은 유지한다. 실행 단가는 높아질 수 있으며 총비용은 실제 실행시간/사용량에 따라 달라진다. 다른 함수CPU와 상시 대기 설정은 유지한다.

## 순차 활성화와 보존

기존 전장은recordStorageVersion을 명시적으로 활성화하기 전까지 원래 형식으로 유지한다. 준비 서버·규칙→호환 사이트 확인→현재 전장 백업/ETag 이관→세부 기록 보존/피드 확인 순서다. 새 시즌은 새 형식에 맞춰 생성한다.

tools/migrate-battle-records.mjs는 기록 인덱스에서 실제 현재 전장을 작은 필드로 찾고, 게임 필드 보존을 확인하며 형식만 바꾼다. 충원 시각·revision·명령·영토·병력·장수·보상·시즌 상태를 임의로 재설정하지 않는다. 저장 도중 충돌하면 ETag로 거절하고 최신 상태에서 재시도한다. 실패한 전달은 대기에 보존된다.

이전 화면에서도 기본 명령과 요약은 유지되나 새 상세 조회는 새로고침한 화면을 사용해야 한다. 새 화면은 구/신 형식을 모두 읽는다. 이전 명령 확인 카드와 임무 UI는 제거 상태를 유지한다.

## 검증과 측정

- 단위 테스트, Firebase 전체 규칙 검증, 최신 저장 모듈의 전달 실패/동시 저장/권한/가지치기·강화·보상·명령 통합 검증을 수행했다. 최종 개수는 배포 기록에 기입한다.
- 동일 저장/명령/난수에서 기존 기록과 요약 기록의 병력·전투 결과·군주·무장 색인·관평 상태 일치를 확인했다.
- 로컬 실제 저장 사본426,663바이트→전달 완료 후294,505바이트(약31% 감소, 상세16개). 병력 집계 결과가 기존과 동일하며100회 로컬 측정에서 집계 중앙값이 약0.05~0.08ms→0.03~0.05ms였다. 이는 그 함수만의 로컬 측정이며 서버 전체 응답 개선율이 아니다.
- 실제 운영에서 테스트 공격·이동·보상 사용은 하지 않는다. 전체 왕복시간의 통제된 전후 비교나 실제 휴대전화 조작은 직접 측정하지 못했다. 공개 파일과 실제 CPU/저장 상태를 확인한다.
- 상시대기·요금제 변경·함수 동시 요청 확대는 적용하지 않는다. 추가 데이터 저장소는 기존 Firebase 프로젝트 안의 경로이며 새 유료 서비스를 가입하지 않는다.
