# 강화 통신 절감 · 직접 실행 계획

사용자 2026-11-03 ‘그러면 그렇게 개선해줘’에 따른 구현·검증·배포 범위다. 강화 계산만 PC로 옮기는 것은 주된 비용인 DB 전송량을 줄이지 못하므로, 선택/확률 미리보기는 기존 로컬 처리를 유지하고 최종 추첨·검증·소모는 서버에서 확정한다.

1. 강화 상세 결과의 이중 누적을 줄인다. 현재 전장의 최근100개 강화 재전송 보호 기록은 ID/군주/순번/시각/불변 상세 버전으로 줄이고 전체 결과는 기존 Firebase 안 enhancementRecords에 분리한다. 전황의 텍스트·순서는 유지한다. 최근100개 보호 건수를 축소하지 않는다.
2. 전장 트랜잭션에서 상세 원본과 전달 대기를 함께 확정한다. 외부 상세 저장과 대기 제거는 원자 업데이트로 처리한다. 실패 시 원본은 전장에 남고 다음 정상 명령·AI 정산·같은 요청 확인에서 전달을 재시도한다. 상세는 보호 기록이나 전황 어느 쪽에서도 참조되지 않을 때만 정리한다.
3. 강화의 서버 확정 응답을 먼저 보여준다. 실시간 전황의 enhanceSeq가 이미 최신이면 후속 조회를 생략한다. 늦으면500ms 후 전황만 확인하고 실패 시2/5초로 최대2회 추가 확인한다. 채팅은 다시 조회하지 않는다. 최신 상태까지 다음 행동을 잠그고 응답 성공을 조회 실패 때문에 미확인 추첨으로 바꾸지 않는다. 확정 잠금은 계정·시즌별로 기기에 보존한다.
4. 성공 확률·기본/보조 재료비·누적 실패·사망·대기·공격/이동 규칙을 유지한다. 서버는 전체 전장 판정과 원자 트랜잭션을 계속 사용한다. 이번 작업에서 도시 한 곳만 읽는 구조로 바꿨다고 표현하지 않는다.
5. 서버·규칙·호환 사이트 배포 후 serverOptimizations/enhancementRecords를 활성화한다. 이 작은 설정은 함수에서60초 캐시한다. 기존 시즌과 다음 시즌은 실제 강화 확정 시 같은 트랜잭션에서 저장 형식이 활성화된다. 현재 시즌의 기존 기록은 백업·ETag 보호 이관으로 병력/시각/순번 보존을 확인하고 분리할 수 있다. 배포 중 구 서버와 새 저장 형식이 섞이지 않게 활성화는 마지막에 한다.
6. 단위/실제 SDK 에뮬레이터로 재시도·응답 유실·상세 전달 실패·동시 강화/다른 명령·권한·가지치기·구 저장 호환을 검증한다. 같은 상태와 행동에서 병력·강화 결과가 같고 전송 바이트가 줄었는지 비교한다. 로컬 계측과 실제 청구 절감률은 구분한다.

새 유료 서비스·상시 인스턴스·게임 규칙 변경은 없다. 비용과 지연 감소량은 배포 후 실제 활동량에도 영향을 받으며0원 운영을 보장하지 않는다.
