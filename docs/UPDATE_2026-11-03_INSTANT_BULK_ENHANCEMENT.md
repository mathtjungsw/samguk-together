# 즉시 연속·일괄 강화 · 2026-11-03

사용자 ‘오케이 그럼 그렇게 수정해줘’에 따른 직접 구현·검증·배포 범위다. 이전의 서버 추첨 유지/통신 경량화 작업을 넘어, 실제 추첨을 클라이언트로 옮긴다.

## 동작과 구현 결정

- PC/휴대전화에서 crypto 난수로 각 강화의 성공·실패를 즉시 결정하고 재료/단계/실패/전사를 강화 창의 임시 전장에 반영한다. 서버 응답 전에 다음 강화를 누를 수 있다. 확률80/60/40%, 보조+10/20/30%p·상한100%, 최대+3·실패 한도·기존 대기는 유지한다.
- 서버는 클라이언트 난수를 재추첨하지 않고 같은 난수로 기존 규칙·대상·재료·소유권·전투 잠금·누적 실패·주둔 한도·순번을 검증한다. 변경 결과 자체를 무검증 덮어쓰지는 않는다. 지인용 게임에서 클라이언트 난수를 신뢰하는 방식이다. 변조한 클라이언트의 난수 공정성까지 서버가 증명하는 설계는 아니다.
- 같은 도시의 여러 병력을 체크하고 각각1회씩 독립적으로 추첨한다. 대상마다 보조재료를 선택하고 총 기본/보조 재료비를 미리 표시한다. 선택 대상은 기본/보조 재료에서 제외하고 재료 중복·부족을 실행 전에 막는다. 모든 선택 대상이 실패 전사해도 주둔1명을 유지하도록 남길 병력을 확인한다. 보조재료는 대상마다 다르게 지정해야 한다.
- 요청ID·순번·대상 현재 단계/실패·난수를 기기 저장소에 먼저 영속화한 뒤 결과를 표시한다. 저장소 실패 시 실행하지 않는다. 여러 번의 클릭을120ms 대기 후 모으고 전송 중 추가 클릭은 다음 전송에 묶는다. 한 전송 최대32회, 기기 미확정 대기 최대128회다. 클릭당 한 도시의 선택 병력은 원래 주둔 정원 이내다.
- 기기별 저장 경로는 프로젝트/계정/시즌으로 분리한다. 지원 브라우저에서는 Web Locks로 같은 기기의 대기 기록 갱신을 직렬화한다. 전송 중인 묶음은 고정하며 응답 유실 시 동일ID/순번/난수로만 재확인한다. 새로고침 후에도 보존된 대기를 복구한다. 여러 기기의 충돌은 서버의 강화 순번과 원자 트랜잭션으로 검증한다.
- 서버는 한 묶음을 하나의 전장 트랜잭션에서 처리한다. 마지막 항목이 실패하면 앞선 항목도 저장되지 않는다. 같은 묶음의 재시도는 기존 강화 기록을 사용한다. 기존 enhancementRecords/전달 대기 구조를 재사용한다.
- ‘저장 중’과 ‘저장 응답 미확인’을 명시한다. 확정된 최신 전황이 올 때까지 공격/이동·보상/부활 등 병력을 바꾸는 일반 명령을 잠근다. 강화 창은 닫아도 저장이 계속되며 다시 열 수 있다. 채팅은 이 강화 대기와 별개로 사용할 수 있다.
- 명확히 거부된 묶음과 그 뒤의 의존하는 미저장 예측은 취소하고 최신 서버 전황으로 복원한다. 결과를 이미 저장했는데 응답만 잃은 경우에는 재료를 다시 쓰지 않는다. 연결/응답 미확인 시 추가 추첨을 멈추고 ‘같은 결과로 다시 저장·확인’으로 복구한다.
- 성공 응답을 받은 뒤 실시간 전황에서 이미 확인되면 중복 조회를 생략한다. 화면이 뒤처지면 전황만 확인하고, 이후 자동 확인은2/5초 간격의 제한된 횟수로 수행한다. 채팅 재조회는 하지 않는다. 서버 함수 수·CPU·최소 인스턴스·요금제는 변경하지 않는다.
